## rs-sdk — controller pre-emption (biggest remaining item)

`mcp/api/index.ts:91` connects in `control` mode, so `execute_code` and a background training
script fight over the single controller slot. The crafting run lost its last **7.6 minutes** to
this: 5 attempts at a bulk script, every one killed by

```
[BotSDK] Pre-empted by another controller - disabling auto-reconnect
error: Connection closed  at /app/sdk/index.ts:218:40
```

The task prompt explicitly tells agents to background long scripts, so this is guidance the
architecture forbids. Three independent fixes, cheapest first:

- [ ] **Don't make pre-emption terminal.** `sdk/index.ts:1569` reuses `intentionalDisconnect` (the
      "I called `disconnect()`" flag) for "I was evicted", so the victim never reconnects even
      after the slot frees a second later. Use a separate `preempted` flag and either reconnect in
      observe mode or retry control with backoff while `GET /status/:username` shows no controller
      (`gateway.ts:703`). **Fixes the failure with zero caller changes.**
- [ ] **Name the cause.** Reject pending actions with a `PreemptedError` carrying the preemptor's
      `sdkClientId`. Today the script prints `Connection closed at index.ts:218` and both agents
      misdiagnosed it — crafting ran `pkill -f mcp/server.ts` and killed its own Bash call (exit 144).
- [ ] **Reject the newcomer instead of killing the incumbent** (`gateway.ts:430-445`): require
      `takeover: true`, and free the slot on socket close / N seconds of no actions so stale
      controllers still can't wedge it. Error then lands on the short-lived client, which can retry.
- [ ] **Or remove the concept:** allow N controllers and serialize at the action level — the
      gateway already tracks `currentActionId` per bot (`gateway.ts:119`). The hazard was always
      two concurrent *actions*, not two sockets.

## rs-bench2 — scoring is sensitive to sampler jitter

`shared/skill_tracker.ts:145-166` resumes the existing tracking file on restart and `takeSample()`
fires immediately (`:207`), so every tracker restart injects an off-cadence sample. Observed gaps
this run: `4.5, 4.6, 13.6, 15.0, 22.5, 22.6`. All 2070 crafting XP landed in a **22.6 s** gap → 28;
the identical action in a 15.0 s gap scores 41, in a 4.6 s gap ~135. ~5× noise on burst skills.

- [ ] `skill_tracker.ts`: record `intervalMs` in the tracking file; on resume, delay the first
      sample to the next cadence boundary; mark samples taken while state is stale
      (`stateAge > intervalMs`) so a frozen client isn't scored as one giant window.
- [ ] `check_xp_rate.ts` + `check_skill_xp.ts`: skip windows spanning a restart or a stale sample,
      and use `deltaMs = max(deltaMs, intervalMs)` so a short gap can't pay a jackpot.
- [ ] Run `scripts/check-xp-normalization-sync.ts` — the divisor logic is standalone-copied into
      5 files. **Decide explicitly whether to re-score history**; this changes published numbers.
- [ ] `generate-tasks.ts:161` claims "Samples are taken on a fixed 15s cadence" — false today.
      Fix the tracker or the sentence.
